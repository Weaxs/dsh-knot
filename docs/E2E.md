# Real end-to-end testing

The `Transport Integration Tests` workflow starts official Hermes and OpenClaw images and a real `dsh web` installation, then executes model-backed tasks through the plugin. These tests do not use protocol mocks and do not treat a successful gateway startup as a passing test.

## Jobs

The matrix reports **18 independent transport/target/protocol jobs**. Each transport is tested separately with `hermes`, `openclaw`, and `dsh`, once through the native adapter and once through the unified ACP provider. Native jobs exercise the existing gateway directly. ACP jobs start a bridge in the target's shared network namespace and connect to it with the official ACP v1 WebSocket transport over the same network path.

| Transport   | Actual network path                                                   | Additional infrastructure                                 |
| ----------- | --------------------------------------------------------------------- | --------------------------------------------------------- |
| `local`     | Plugin → loopback-published gateway port                              | Official agent containers or the DSH test image           |
| `tailscale` | Plugin → runner tailnet → sidecar tailnet IP → gateway                | Tailscale runner action and one sidecar per job           |
| `headscale` | Plugin → self-hosted Headscale tailnet → sidecar tailnet IP → gateway | Headscale control plane and one Tailscale sidecar per job |

Every job tests exactly one target:

1. Check protocol health.
2. Start a task that asks the model to remember and return a random token.
3. Require a completed result containing that token.
4. Continue the same remote session and ask the model to repeat it.
5. Require the second result to contain the same token. Hermes also verifies that the session appears in history.

The second response verifies a real model invocation and remote session continuity. A manual `workflow_dispatch` without required credentials fails explicitly. Push and scheduled runs emit a visible warning and skip only the missing E2E jobs; they never substitute mocks or report skipped jobs as passing.

## Required secrets

Configure these repository or organization Actions secrets:

| Secret              | Used for                                                                                                                          |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `OPENAI_BASE_URL`   | OpenAI-compatible model API base URL, normally ending in `/v1`                                                                    |
| `OPENAI_API_KEY`    | Credential for that model API                                                                                                     |
| `OPENAI_MODEL_NAME` | Exact model ID used by all three targets                                                                                          |
| `TAILSCALE_AUTHKEY` | **Reusable and ephemeral** Tailscale pre-auth key (`tskey-auth-...`) for the runner and sidecar. Required only by Tailscale jobs. |

Enable both **Reusable** and **Ephemeral** when generating the [Tailscale auth key](https://tailscale.com/docs/features/access-control/auth-keys). The preflight can check the key prefix, which is the same for both persistent and ephemeral keys.

Headscale needs no external account or secret. Each job creates its own user and pre-auth keys. The DSH launch token is generated by `dsh web` inside the container and passed through a temporary file; it is not a repository secret.

`HERMES_API_KEY` and `OPENCLAW_GATEWAY_TOKEN` in the workflow are fixed **ephemeral test gateway passwords**, not production credentials. They exist only inside the short-lived CI environment.

## Model configuration

- Hermes receives a generated `config.yaml` with `model.provider: custom`, `model.default`, `base_url`, and `key_env: OPENAI_API_KEY`.
- OpenClaw receives a generated `openclaw.json` using `models.providers.openai` with `openai-completions` and `agents.defaults.model.primary = openai/<model>`.
- DSH receives a profile patch targeting `llm-pi-ai`. It declares the exact model on an `openai-completions` route, enables `low` reasoning for models that cannot disable thinking, disables the unsupported `developer` role for GLM compatibility, and selects the model through native `session/selectModel` before prompting.

No tools are enabled for the test task. Containers use AliDNS (`223.5.5.5`) and DNSPod (`119.29.29.29`) because the configured model endpoint uses region-specific DNS answers. The runner also tries DoH providers and writes a returned IPv4 address into container `/etc/hosts`; a public regional-DNS fallback mapping in `.github/workflows/e2e.yml` is used only when those providers return NXDOMAIN. Tailscale sidecars do not replace those resolvers.

If `OPENAI_BASE_URL` points to `127.0.0.1` or `localhost`, the generated container configuration rewrites the host to `host.docker.internal`. On Linux, Compose maps that name through `host-gateway`.

## OpenClaw device approval

- Local connections use OpenClaw's trusted loopback auto-approval behavior.
- Tailscale and Headscale are remote connections. A sidecar watches `openclaw devices list --json` and calls `openclaw devices approve <requestId>` for new test devices.

This is real OpenClaw pairing, not a bypass in the plugin. Each test run persists its own Ed25519 device identity for that gateway connection.

## Remote DSH

The DSH image starts `dsh web` on loopback, captures its random launch token, and exposes a test-only HTTP bridge that rewrites the Host header to that loopback authority. The adapter then uses the native endpoints:

- `GET /connect?token=...&interactions=none`
- `session/create`
- `session/selectModel`
- `session/prompt`
- `session/wait`
- `session/list`
- `session/cancel`

This keeps DSH's authenticated browser trust boundary intact while exercising the same RPC path over Local, Tailscale, and Headscale.

## Running the workflow

Run **Transport Integration Tests** manually through `workflow_dispatch`, optionally selecting one transport, target, and protocol (`native` or `acp`), or let it run when E2E-related files change on `main` or on its weekly schedule. The normal `CI` workflow separately runs Biome, TypeScript, unit/protocol tests, build, and package checks without model credentials.

To run one transport/target locally with Docker and the same credentials:

```bash
export OPENAI_BASE_URL='https://your-endpoint.example/v1'
export OPENAI_API_KEY='...'
export OPENAI_MODEL_NAME='your-model'
bash .github/e2e/scripts/run-compose.sh local dsh
E2E_PROTOCOL=acp bash .github/e2e/scripts/run-compose.sh local dsh
```

For Tailscale mode, also export `TAILSCALE_AUTHKEY` and connect the local machine to the same tailnet first. The Headscale script starts its own control plane and joins the local machine to it. All three modes use Docker to run the target agents.

## Logs and cleanup

The script logs out the ephemeral Tailscale sidecar before stopping the container. The Tailscale GitHub Action logs out the runner in its post step. After an abrupt stop, Tailscale removes ephemeral devices after a period of inactivity. See [Tailscale ephemeral nodes](https://tailscale.com/docs/features/ephemeral-nodes).

Each script uses a unique Compose project and removes containers, networks, and volumes on exit. On failure, the workflow uploads container and adapter logs as artifacts. Logs should not contain model credentials, but hostnames, device IDs, session IDs, and model output are expected test data.

Model calls cost money and can take several minutes. Each job has a 35-minute timeout, and adapter tasks have their own timeout as well.
